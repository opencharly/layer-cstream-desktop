# 2026.242.1505 — feat: advance pod-cstream to the build shipping the consumer frame probe

## Summary

Advance `pod-cstream` from `v2026.242.1421` to `v2026.242.1445`, the build that ships
`/usr/local/bin/cstream-frame-probe` — the consumer-side probe that pulls a frame back **through the
negotiated WebRTC track**. It is what the `cstream: frame` verb calls in the venue.

Neither existing probe can stand in for it:

| probe | reads | fails on an encode/transport defect? |
|---|---|---|
| `stream-probe` | the producer's own pipeline tap | **no** |
| `wl: screenshot` | the compositor | **no** |
| `cstream-frame-probe` | what a real consumer decodes | **yes** |

That gap is exactly what let a missing `webrtcbin` hide while every producer-side check passed and
not one byte reached a consumer.

### 2. The pinned tag was gated by a live bed before it merged

In `pod-cstream#8` the probe ran as a **real charly check** against a freshly built image, asserting
on `FRAME-OK` — a string it prints only after a frame has actually arrived and been copied:

```
charly check run check-cstream-pod: PASS (steps=13)
  check-live          61 steps: 57 passed, 0 failed, 4 skipped
  check-live-rebuild  61 steps: 57 passed, 0 failed, 4 skipped
```

Both legs moved from 60 steps / 56 passed to 61 / 57 — that one extra step is the probe.

### 3. The probe has since been exercised through the verb

`plugin-cstream#2` (merged, `v2026.242.1502`) authors `cstream: frame` against this probe with
`artifact_min_bytes: 5000` and `artifact_not_uniform: true`, and that step passes — so the frame
this advance makes available is a decoded, non-uniform one reaching a host artifact.
