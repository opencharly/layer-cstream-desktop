# 2026.242.1424 — fix: advance pod-cstream to the build that can actually carry media

## Summary

Advance `pod-cstream` from `v2026.242.1124` to `v2026.242.1421` — the first build whose WebRTC
transport can actually carry media.

**What the advance fixes.** The stack negotiated a WebRTC session end to end and then carried **no
media**, with no ICE or DTLS error to point at. The cause, read off the producer's own log:

```
SessionPipelineError { session_id: "…", peer_id: "…",
                       details: "Failed to make element webrtcbin" }
```

`webrtcsink`/`webrtcsrc` come from `gst-plugin-rswebrtc` and were present, but they construct a
**`webrtcbin` per session internally**, and that element ships in `gst-plugins-bad` — which was
never installed, only `gst-plugins-bad-libs` (the shared libraries, pulled in transitively). So
`libgstwebrtc.so` was absent. The construction failure is a **WARN, not an error**, so the sink
registered, the session started, the offer was never sent, and every consumer waited until timeout.

That is why earlier investigation of this stack found "no ICE/DTLS error": there was no `webrtcbin`
to perform ICE or DTLS at all.

Measured on one pod with the package as the only variable:

```
BEFORE  webrtcbin ABSENT   frames received 0      "Failed to make element webrtcbin" x1
AFTER   webrtcbin PRESENT  frames received 1683   (55,988,362 bytes)                 x0
```

**The tag also carries a new gate.** `cstream-webrtcbin-registered` asserts the element itself. Its
neighbour `cstream-webrtcsink-registered` **passed throughout the entire outage** — it checks that
the sink registers, which says nothing about whether it can serve a session. Registration is not
capability, the same trap the VA encoder gate already covers by opening the encoder.
